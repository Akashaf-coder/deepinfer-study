# 第 13 课：性能基准与实验方法

> 推理系统的性能数字，90% 的争议来自"怎么测"。本课先讲测量方法，再讲数字。

## 本课目标

1. 说清 benchmark 的三个指标（prefill throughput、avg_SPS、decode throughput）的定义与陷阱。
2. 理解为什么 prefill 和 decode 要**解耦测量**。
3. 会读 Pareto 图，知道每个点的配置。
4. 能设计一个单变量对照实验，并避免五个常见错误。

## 三个指标

来自 `examples/README.md`：

### 1. Prefill throughput（tokens/s/GPU）

- 跳过 5 个 warmup chunk；
- 取最后 11 个 prefill 样本 → 10 个稳态区间；
- 这 10 步处理的 token 数 ÷ 总时长 ÷ 设备数；
- 第一个样本只提供起始时间戳，token 不计入。

### 2. Decode avg_SPS（steps/s）

- 跳过 50 个 warmup step + 60 个 logged step；
- 取最后 61 个 full-batch decode 样本 → 60 个稳态区间；
- 剔除与 MoE LB 统计 flush 冲突的区间（EP all_gather，抖动十几 ms）；
- 同时打印 `max_step`（最慢单步），正常应接近 `1000 / avg_SPS`。

### 3. Decode throughput（tokens/s/GPU）

```
avg_SPS × decode_num_requests × (1 + nextn) / cp_size
```

注意：这是**全接受假设**（每请求每步产出 `1+nextn` 个 token），不是真实接受率。所以它衡量的是"调度+执行能力"，不是"有效吞吐"。真实有效吞吐要乘接受率。

## 为什么 prefill/decode 解耦

`benchmark.py` 的设计：

- `--prefill_batch_size` / `--non_cached_tokens` 只影响 prefill 的 chunk 大小和后缀长度；
- `--decode_num_requests` 只控制 decode batch；
- prefill 需要的请求数 `N` 由"要多少个 chunk"反推，与 decode batch `K` 无关（上限 512）。

如果耦合测量，prefill 的数字会被 decode 的 batch 污染（KV 占用、显存压力）。解耦后每个指标都有独立的工作点。

唯一的耦合：decode 复用 prefill 产出的共享前缀 KV。所以整批请求按 `max(N, K)` 创建。

## 为什么要"烧 step"

- 测量窗口前后各留一段"烧"的 step，目的是避开周期性事件（LB 统计 flush、日志、JIT、GC）；
- profiler 窗口放在最后，因为 profiler 退出后仍有 7–11% 的残余减速（官方实测，bsz=1）；
- 所以 trace 里的 step 时间**不能**用来算 SPS，只能看 kernel 组成。

## Pareto 图怎么读

仓库里的三张图（`doc/images/`）：

### Prefill（EP4DP4，384+32 experts，131k ctx，bounded replay 140）

| batch (tokens/DP rank) | 4,096 | 8,192 | 16,384 | 32,768 | 65,536 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 吞吐 (tokens/s/GPU) | ~60k | ~72k | ~81k | ~86k | ~88k |
| 延迟 (ms/step) | ~70 | ~115 | ~200 | ~370 | ~730 |

读法：
- 横轴是延迟，纵轴是吞吐，每个点是"一个 batch 大小"；
- 2 万 token 后曲线饱和：prefill 的瓶颈从 GEMM 变成 attention 的 KV 读取；
- 这条曲线的收益主要来自 **YoCo 截断**（算一半层），不是调度。

### Decode（EP64DP64，384+64 experts，131k ctx，nextn=3，75% 接受）

| 并发 (req/rank) | 8 | 16 | 32 | 64 | 128 | 256 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 吞吐 (tokens/s/GPU) | ~2.5k | ~5k | ~9.5k | ~15.5k | ~22.5k | ~26k |
| 单用户速度 (tokens/s/user) | ~325 | ~315 | ~298 | ~249 | ~180 | ~104 |

读法：
- 横轴是单用户速度，纵轴是每 GPU 吞吐；
- 这是一条典型的"吞吐-交互性"trade-off 曲线；
- 生产工作点通常在 200–300 tok/s/user（约 3–5 ms/token）；
- 26k tok/s/GPU 对应 104 tok/s/user，已经接近交互可接受的下限。

### Wide-EP（EP8 vs EP64，131k ctx，nextn=3，75%）

| 单用户速度 | EP8DP8 | EP64DP64 | 倍数 |
| --- | ---: | ---: | ---: |
| ~175 tok/s | ~15k | ~22.5k | 1.5× |
| ~250 tok/s | ~8k | ~16k | 2.0× |

读法：
- 同样的交互性下，EP64 的吞吐更高；
- 低交互性区间收益更大（因为 MoE 的每卡访存量被摊薄）；
- 这是"decode 用能拿到的最大的 EP"的量化依据。

## 实验设计：单变量矩阵

| 实验 | 变量 | 观察指标 | 预期 |
| --- | --- | --- | --- |
| E1 | `DEEPINFER_USE_NEXTN_DECODE=0/3/5` | accept_rate、decode tok/s、SPS | nextn↑ → 吞吐↑，但接受率↓ |
| E2 | `DEEPINFER_ENABLE_MTP_VARLEN=0/1` | 平均验证长度、吞吐 | 高并发才有正收益 |
| E3 | `--disable_eplb` | `moe_lb`、decode tok/s | 关掉后 `moe_lb`↑、吞吐↓ |
| E4 | `YOCO_PREFILL_TRUNCATION_MODE=off/mask/compact` | prefill 延迟、输出等价性 | compact 最快，需 yoco_equiv 验证 |
| E5 | `--cp 1/2/8` | prefill 吞吐、通信开销 | CP 提升长序列吞吐，但有 all-gather 成本 |
| E6 | `ZERO_OVERHEAD_SCHEDULING=0/1` | SPS、bubble 时间 | 开启后 SPS↑、bubble↓ |
| E7 | `BATCH_INVARIANT=0/1` | 输出是否逐 bit 一致 | 开启后一致，性能略降 |
| E8 | `gpu_memory_utilization=0.8/0.9` | 可用 block 数、OOM | 高利用率 → 更多并发，但 graph 可能 OOM |

每个实验只改一个变量，其他全部固定；每次跑至少 3 次取中位数。

## 五个常见测量错误

1. **用 profiler 的 step 时间算吞吐**：profiler 本身有 7–11% 残余减速，还会让单步膨胀。
2. **把 prefill 和 decode 的数字混在一起**：它们是解耦测量的，工作点不同。
3. **忽略接受率**：`decode throughput` 是全接受假设，真实有效吞吐要乘接受率。
4. **没等稳态**：warmup 不够，JIT、CUDA Graph 捕获、页表都会影响前几十步。
5. **跨硬件/跨模型对比**：26k tok/s/GPU 是 SM100 + V4.1 + FP4 KV 的结果，不能和 H100 上的 vLLM 直接比。

## 如何复现

```bash
export WORLD_SIZE=1 RANK=0 CUDA_VISIBLE_DEVICES=0,1,2,3,4,5,6,7

# 默认配置
python examples/benchmark.py

# 低延迟：单请求 decode
python examples/benchmark.py --decode_num_requests 1

# 128k 上下文 + YoCo 截断
python examples/benchmark.py --decode_num_requests 64 --context_length 131072 --yoco_clip

# 扫 Pareto
bash examples/sweep/run_sweep.sh decode ep64-decode-128k 131072 3 0.75
bash examples/sweep/run_sweep.sh prefill ep64-prefill-128k 131072
```

输出：
- `sweeps/<tag>/results.jsonl`（每个点一行）；
- `sweeps/<tag>/<mode>_pareto.png`；
- `--result_jsonl <FILE>` 可以把原始量（窗口步数、token 数、耗时、avg_SPS）写出来。

## 读 trace 的三个看点

1. **forward 和 sample 之间有没有 gap**：有 gap = ZOS 没生效或 CPU 跟不上；
2. **MoE kernel 的占比**：EP 越大，MoE 通信占比越高；
3. **是否出现异常的短 kernel 串**：可能是 JIT 没缓存、graph 没命中，或 fallback 到 eager。

`PROFILE=1` 的 trace 会把 prefill 和 decode 两段拼在一起，包含 2 个 full-chunk prefill step + 3 个稳态 decode step。

## 生产数据（Q&A，仅作背景）

- 单集群每天 155 万亿 token；
- 谷时每 GPU 小时收入 38 美元；
- KV cache 保留 3 天（agent）/ 7 天（chatbot）；
- 3FS 提供约 100 PiB SSD；
- 负载均衡后达到完美均衡离线 benchmark 的约 80%。

这些数字说明"规模"，但**不能**用来推算单机性能——它们包含路由、缓存命中、定价等系统级因素。

## 易错点

1. **以为 `avg_SPS` 就是吞吐**：它只是 steps/s，要乘 batch 和 token 数。
2. **以为 `max_step` 越接近平均越好**：偶尔的长尾是正常的（GC、flush），持续偏离才是问题。
3. **在 sweep 里改固定配置**：同一个 `results.jsonl` 里的点必须同配置，否则绘图断言失败。
4. **多节点跑 sweep**：只有 dp_rank 0 写 jsonl，其他节点正常退出。
5. **用 `--result_jsonl` 覆盖已有文件**：它是 append 模式，注意清理。
