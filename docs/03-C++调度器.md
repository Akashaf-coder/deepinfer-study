# 第 03 课：C++ 调度器——每一步到底调度了什么

> `csrc/engine/scheduler.hpp` 是全仓库最值钱的文件。本课按"决策 → 裁剪 → 分配 → 收尾"四段拆开讲。

## 本课目标

1. 说清 `waiting` / `running` / `prompted` 三个队列的状态机。
2. 理解 NORMAL 引擎的**两轮投票**，以及它防的两个死锁。
3. 能手动推演：给定 waiting 里的 3 个请求和剩余 block，这一步会调度谁、切多少 token。
4. 记住 10 条调度器不变量，调试时能快速定位断言。

## 为什么用 C++

一个 decode step 的调度工作量：~100 个序列 × 每序列几十个字段 + block 分配 + 元数据构造。Python 做这件事有两个成本：

1. **对象开销**：每个 `Sequence` 的字段访问、列表操作都走 Python 对象协议；
2. **GIL 与 GC**：高频小对象会触发 GC 抖动。

DeepInfer 的选择是把整个调度器（含 `Sequence`、`BlockManager`）搬进 C++，Python 每步只传一个对象池指针、拿回两个对象（`seq_metadata_list`、`scheduler_outputs`）。代价是调试要跨语言、改调度要重编译。

## 数据结构

```cpp
struct Scheduler {
    std::deque<SequencePtr> waiting;    // 等待 prefill（或被抢占后重算）
    std::deque<std::pair<SequencePtr, bool>> prompted;  // prefill 完成、待转入 running（bool=forked）
    std::vector<SequencePtr> running;   // 正在 decode
    ...
};
```

| 队列 | 元素 | 谁推进 | 备注 |
| --- | --- | --- | --- |
| `waiting` | 新请求、被抢占的请求 | `_schedule_prefill` 弹出 | 被抢占的会 `push_front` |
| `prompted` | 本步 prefill 完的请求 | `_schedule_decode` 的 `admit` | forked 需要 clone block |
| `running` | 活跃 decode 请求 | `_schedule_decode` 全量处理 | 每个 decode step 必须全部调度或抢占 |

锁：`BlockManagerMutexAcquire` 同时锁 `block_manager` 和 `state_manager`（如果存在）。所有 `*_nolock` 接口都假设已持锁。

## 决策：这一步做 prefill 还是 decode

`_schedule()`（`scheduler.hpp:288`）先按引擎类型分流：

```cpp
switch (engine_type) {
case EngineType::PROMPT:     return _schedule_prefill(acquire);
case EngineType::COMPLETION: return _schedule_decode(acquire);
case EngineType::NORMAL: { ... 投票 ... }
}
```

NORMAL 引擎的投票（原文注释非常清楚，建议整段读）：

```cpp
bool is_any_point = (decode_step != 0) && (decode_step % prefill_any_attempt_interval == 0);
bool is_all_point = (decode_step % prefill_attempt_interval == 0);
if (!is_any_point && !is_all_point) return _schedule_decode(acquire);

bool want = (get_gpu_cache_usage() <= GPU_CACHE_PREFILL_WATERMARK) && _has_prefill_waiting();
if (is_any_point)
    do_prefill = (_dp_allreduce(want ? 0 : 1, MIN) == 0);   // ANY：任一 rank 想
else
    do_prefill = (_dp_allreduce(want ? 1 : 0, MIN) == 1);   // ALL：全员都想
```

三个关键点：

1. **为什么需要投票**：同一 DP 组的所有 rank 必须"同型"（要么都 prefill，要么都 decode），否则集合通信会对不上。`decode_step` 在每个 rank 上同步递增，所以投票点一致。
2. **ALL 点**防"陪跑"：一个 rank 有活、其他没活时，硬做 prefill 会让其他 rank 空转一个 prompt step。
3. **ANY 点**防饿死：孤立 rank 的 prefill 最多等 `prefill_any_attempt_interval` 个 decode step。

**第二轮投票**（很多人会漏）：

```cpp
bool any_scheduled = (_dp_allreduce(outputs ? 0 : 1, MIN) == 0);
if (!any_scheduled) return _schedule_decode(acquire);
```

`want` 只代表"waiting 非空"，但 `_schedule_prefill` 可能因为 slot 满/block 不够而空手。如果全组都空手却硬返回空 prompt，`schedule()` 会把 `decode_step` 清零，下一步又投票、又空手——**死循环**。所以第二轮确认"真有人排出了 prefill"，否则转 decode。

## 裁剪：prefill 选谁、切多少

`_schedule_prefill()`（`scheduler.hpp:350`）的主循环：

```cpp
while (!waiting.empty()) {
    auto &seq = waiting.front();
    if (seq->is_finished()) { ignored_seqs.push_back(...); waiting.pop_front(); continue; }
    if (!seq->schedule.schedulable) break;

    int num_prompt_tokens = seq->get_len() - seq->cache.num_tokens;
    bool prefix_caching_hit = false;
    if (seq->cache.block_table.empty()) {
        prefix_caching_hit = true;
        if (seq->get_len() > prompt_limit) { ... FINISHED_IGNORED ... }
        auto can_allocate = _can_allocate_with_state(seq->get_num_blocks());
        if (can_allocate == LATER) break;      // 等下一轮
        ...
    }
    ...
}
```

裁剪的五个维度（按代码顺序）：

| 维度 | 变量 | 作用 |
| --- | --- | --- |
| 单条 prompt 上限 | `prompt_limit` | 不开 chunked prefill 时 = `min(max_model_len, max_num_batched_tokens)` |
| 本步 token 预算 | `max_num_batched_tokens` | 所有 seqlen_q 之和 |
| KV 总长度预算 | `prefill_max_sum_seqlen_k` | 防长上下文把 attention 的 K 维和算爆 |
| 并发序列数 | `max_num_seqs` | |
| block / state slot | `_can_allocate_with_state` | 返回 `LATER` 就 break |

切分对齐（`_adjust_chunk_size`）：
- 不能切进 image pad 区域（多模态）；
- 对齐 `cp_align = cp_size * 2`；
- 支持 `chunk_checkpoints` 强制断点（benchmark/测试）；
- chunked prefill 时，NORMAL 引擎**一轮只推进一个 chunk**，然后 `break`（让 decode 有机会插入）。

## 分配：block 与 state

```cpp
if (!is_chunked) {
    num_curr_seqs += 1;
    seq->schedule.status = RUNNING;
    allocate_mtp_info_slot(*seq);
}
```

- 非 chunked：序列一步变 RUNNING，占用一个 MTP info slot；
- chunked：仍留在 waiting，`chunked_rest_len` 记录剩余；
- block 分配走 `block_manager->allocate_nolock(n)`，失败就 `LATER`；
- state slot 走 `state_manager`（只有 SWA/压缩状态需要）。

## decode：LCFS 与抢占

`_schedule_decode()`（`scheduler.hpp:553`）的步骤：

1. `free_finished_seqs()` 回收已结束的；
2. 兜底清理 waiting 里已终结的 seq（否则 `has_unfinished` 永远为真，ALL 投票被永久压死——代码注释明确写了这个坑）；
3. `prompted` 头部转入 running（forked 要先 clone state + 尾 block）；
4. **按 output_len 降序排序**，然后从尾部（output 最短的）开始调度 —— 即 **LCFS（Last Come First Served）**；
5. block 不够时，从头部（output 最长的）抢：
   ```cpp
   while (!block_manager->can_allocate_single_nolock() && r - l > 1) {
       _preempt(running[l], ignored_seqs); l += 1;
   }
   ```
6. 每个被调度的 seq 调 `_append_slot()`（分配新 token 需要的 block，可能触发 copy-on-write）；
7. `TORCH_CHECK(l == r)`：**decode 步必须处理完 running 里的每一个 seq**（要么调度、要么抢占），不允许"留一部分下步再说"。

LCFS 的含义：新请求（output 短）优先，长输出请求在显存紧张时先被抢。这是为了**降低尾延迟**——长输出请求本来就要跑很久，抢它一次重算的边际成本比抢新请求低？更准确地说，是让短请求尽快完成，减少平均排队时间。代码没有解释动机，这是"推断"。

抢占的两种结局（`_preempt`，`scheduler.hpp:766`）：

| 条件 | 行为 |
| --- | --- |
| `stop_preempted_request=true` | 直接 `FINISHED_PREEMPTED`，回传 `ignored_seqs` |
| 请求有 SO 状态 | 同上（SO 自动机不能重算） |
| 其它 | `reset_for_recompute()`，`push_front(waiting)`，下一轮重新 prefill |

## 收尾：构造 metadata

`schedule()`（`scheduler.hpp:697`）在拿到 `SchedulerOutputs` 后，为每个 seq 构造 `SequenceMetadata`：

```cpp
int seqlen_q = scheduler_outputs.seqlens_q[i];
int seqlen_k = seq->cache.num_tokens + seq->schedule.total_inflight_tokens + seqlen_q;
int position_end = prompt_run ? seqlen_k : seqlen_k - seqlen_q + max_seqlen_q + nextn;
TORCH_CHECK(position_end <= runtime_max_model_len, ...);
```

- `seqlen_k` 把 **inflight tokens** 算进来：ZOS 下上一步的 token 可能还没提交；
- `position_end` 给 RoPE cache 等按 position 索引的 buffer 做上界检查；
- 同时累加 `sum_seqlen_qxk`、`max_seqlen_k`，`log_stats` 时调 `FlopsEstimator::calc_flops()` 估 FLOPs。

## 图解：一个 NORMAL step 的决策树

```
decode_step++
  │
  ├─ 不是投票点 ─────────────────────────► _schedule_decode（LCFS）
  │
  └─ 是投票点
       ├─ GPU cache > 90% 或 waiting 空 ──► _schedule_decode
       ├─ ANY 点：allreduce(MIN) 任一想要 ─┐
       ├─ ALL 点：allreduce(MIN) 全员想要 ─┤
       │                                   ▼
       │                            _schedule_prefill
       │                                   │
       │                     ┌─────────────┴─────────────┐
       │                     │ 排出 batch                 │ 空手
       │                     ▼                            ▼
       │              第二轮 allreduce              第二轮 allreduce
       │                     │                            │
       │              有人排出 → 返回            全员空手 → decode
       │              别人排出 → 空 prompt 陪跑
       └─────────────────────────────────────────────────────
```

## 10 条调度器不变量

调试时先对这几条：

1. `sum(seqlens_q) == num_batched_tokens <= max_num_batched_tokens`
2. `seqlen_q + cache.num_tokens <= seq.get_len()`
3. `position_end <= runtime_max_model_len`
4. decode 步 `running` 必须清空（全部调度或抢占）
5. COMPLETION 引擎必须 `stop_preempted_request=true`
6. 每步 MTP info slot 使用数 == running 大小（nextn>0 时）
7. `prefill_max_sum_seqlen_k >= prompt_limit`
8. chunk 切分对齐 `cp_size*2`，且不切进 image pad
9. `block_table.size() == ceil(get_num_blocks())`（允许尾部预留）
10. `log_stats` 关闭时 FLOPs 可以是 0，但 `sum_seqlen_qxk` 仍要正确

## 易错点

1. **以为 prefill 每步都做**：NORMAL 引擎只在投票点做。
2. **以为 `want=true` 就一定 prefill**：还要第二轮确认。
3. **以为 decode 可以"少调度几个"**：`TORCH_CHECK(l==r)` 会直接崩。
4. **以为抢占一定重算**：SO 请求和 `stop_preempted_request=true` 时直接结束。
5. **以为 `schedulable=false` 是 bug**：它是外部（entrypoint/LB）控制流量的手段。
