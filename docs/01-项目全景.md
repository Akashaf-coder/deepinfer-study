# 第 01 课：项目全景——边界、血统、代码地图

> 本课不深入任何算法，只解决三个问题：它从哪来？由什么组成？刻意缺了什么？

## 本课目标

1. 说清 DeepInfer 的**血统**：哪些文件来自 vLLM，哪些是 DeepSeek 自研。
2. 用一张表建立**代码地图**：12 个模块的行数、职责、优先级。
3. 理解**构建流水线**：`build.sh` → vendor wheel → `_C` 扩展 → TileLang JIT。
4. 记住**五个边界**，避免在错误的方向上浪费时间。

## 核心概念

### 1.1 血统：一个 fork 的三种基因

```bash
grep -rl "Derived from vLLM" deepinfer | sort
```

结果覆盖了引擎主干：`llm_engine.py`、`worker/base.py`、`worker/model_runner.py`、`model_executor/model_loader.py`、`layers/sampler.py`、`sequence.py`……

三种基因：

| 基因 | 来源 | 体现 |
| --- | --- | --- |
| 引擎骨架 | vLLM | `LLMEngine`、`Worker`、`ModelRunner`、`CacheEngine`、`Sequence` 的命名与分层 |
| 异步调度 | SGLang / NanoFlow | ZOS 的四段流水线（Q&A 明确写 "Following SGLang, NanoFlow"） |
| 图/编译思路 | TensorRT-LLM | CUDA Graph、kernel 融合、profile 驱动的调优 |

但**调度器被重写了**：vLLM V1 用 Python 调度，DeepInfer 用 C++（`csrc/engine/`）。这是最大的结构性差异。

### 1.2 代码地图（按行数）

| 模块 | 文件数 | 行数 | 职责 | 优先级 |
| --- | ---: | ---: | --- | :---: |
| `deepinfer/engine/` | 6 | 1,957 | 引擎编排、参数、统计 | ★★★★★ |
| `deepinfer/worker/` | 10 | 2,805 | 执行、缓存、CUDA Graph | ★★★★★ |
| `csrc/engine/` | 20 | ~5,000 | 调度器、BlockManager、Sequence、ZOS | ★★★★★ |
| `deepinfer/model_executor/models/` | 30+ | 7,051 | V4 模型结构 | ★★★★★ |
| `deepinfer/model_executor/layers/` | 102 | 24,996 | 层 + TileLang 算子 | ★★★★ |
| └ `layers/tilelang_ops/` | 63 | 23,331 | CUDA/Ascend 双份算子 | ★★★★ |
| `deepinfer/model_executor/eplb/` | 4 | 792 | 专家负载均衡 | ★★★★ |
| `deepinfer/structure_output/` | 5 | 595 | 结构化输出 | ★★★ |
| `deepinfer/ve/` | 9 | 979 | 多模态预处理 | ★★★ |
| `deep_cluster/` | 8 | 656 | 硬件发现、NUMA | ★★ |
| `examples/` | 15 | 3,018 | 入口、benchmark、sweep | ★★★★★ |
| `tests/` | 20 | 3,117 | 单测 + PPL 金标准 | ★★★ |

一个反直觉的事实：**42% 的 Python 代码是 kernel**（23,331 / 54,929）。真正的"框架逻辑"只有约 3 万行，其中还有大量注释和类型定义。

### 1.3 五个边界

| 边界 | 证据 | 影响 |
| --- | --- | --- |
| 单模型 | README 只列 V4.1-Flash；`ModelRegistry` 只有 V4 系列 | 无法换模型 |
| 单代硬件 | `get_bf16_tflops_limit()` 只认 SM10 / Ascend | H100/A100 跑不了 |
| 无在线服务 | `entrypoints/` 只有 `llm.py`；无 HTTP server | 自己写 serving |
| 无 TP | `grep -r tensor_parallel` = 0 | 并行策略只有 EP/DP/CP |
| 系统不完整 | Q&A 列出 KV store / 四类 LB / autoscaling 未开源 | 复现不了生产数字 |

### 1.4 构建流水线：三步

```bash
export DEEPINFER_ACCELERATOR=nvidia
./build.sh
```

`build.sh` 做三件事：

1. `pip install -r requirements-nvidia.txt`（torch 2.13+cu132、flash-attn-4 beta、tilelang 0.1.15……）
2. `scripts/build_vendor.sh`：`git submodule update --init`，然后逐个 `python setup.py bdist_wheel` 构建 DeepSelect / FlashMLA / DeepEP / DeepGEMM（Ascend 换 -Ascend 版本），最后 `pip install --no-deps --no-index`
3. `scripts/build.sh build`：`setup.py build` 编译 `csrc/` 成 `deepinfer._C`，把 `.so` 软链到 `deepinfer/_so/<platform>/`

运行时还有一层：TileLang 算子在首次 import 时 **JIT 编译**，缓存到 `DEEPINFER_JIT_CACHE_DIR`。所以第一次跑很慢，第二次快。

### 1.5 模块之间的依赖方向

```
entrypoints → engine → worker → model_executor → layers
                  │        │            │
                  │        │            └→ tilelang_ops（CUDA / Ascend）
                  │        └→ deep_cluster（硬件发现）
                  └→ csrc/engine（C++，通过 pybind 暴露）
```

设计上尽量保持单向；但 `engine/llm_engine.py` 直接 import 了 `model_executor` 里的 `ModelMetadata`、`CompressedTokenizer`，属于"编排层知道模型细节"的妥协。

## 源码解析

### 1.6 入口：`LLM` 只是薄封装

`deepinfer/entrypoints/llm.py`：

```python
class LLM:
    def __init__(self, model, tokenizer=None, ..., expert_parallel_size=1, ...):
        kwargs.setdefault("disable_log_stats", True)
        kwargs.setdefault("stop_preempted_request", False)
        engine_args = EngineArgs(..., offline_inference=True, **kwargs)
```

值得注意的默认值：
- `disable_log_stats=True`：离线场景默认不打印每步统计；
- `stop_preempted_request=False`：允许重算被抢占的请求；
- `offline_inference=True`：这个 flag 会影响调度器行为（比如是否允许某些 PD 操作）。

### 1.7 C++ 扩展的暴露方式

`csrc/engine/pybind.cpp` 把 `Scheduler`、`BlockManager`、`Sequence`、`SequenceMetadata`、`RequestOutput`、`process_MTPInfo` 等直接暴露给 Python。Python 侧这样用：

```python
from deepinfer._C.engine import (
    BlockManager, Scheduler, SchedulerOutputs,
    SequenceMetadata, SequenceMetadataPool, RequestOutputPool,
)
```

这带来两个后果：
1. **调试要跨语言**：Python 断点看不到 C++ 内部状态，只能靠日志/`gdb`；
2. **接口是手写的**：没有自动生成，字段变更要同时改 `.hpp` 和 `.pyi`（`scripts/gen_stub.sh` 生成 stub）。

### 1.8 测试即文档

`tests/` 里最值得读的三个：

| 测试 | 它其实在解释什么 |
| --- | --- |
| `tests/engine/test_sequence.py` | `Sequence` 的状态机、block 生命周期 |
| `tests/models/test_batch_invariant.py` | batch-invariant 到底保证什么 |
| `tests/worker/test_state_cache_ops.py` | state slot 的拷贝/存储语义 |

PPL 金标准在 `tests/models/offline_decode_ppl.json`，按平台/负载分组，逐样本精确比对。这解释了为什么引擎要花力气做**确定性采样**。

## 图解：仓库的"三圈"

```
外圈：系统（未开源）
  Entrypoint ×3 / KV Store(3FS) / LB ×4 / Autoscaling / Recipe
        │
中圈：引擎（本仓库）
  LLMEngine / Scheduler(C++) / Worker / CacheEngine / EPLB / SO
        │
内圈：模型与 kernel（本仓库）
  DeepseekModel / V4Attention / MoE / TileLang ops / vendor libs
```

学习时最容易犯的错：**拿外圈的行为去中圈找代码**。比如"compute quota 解二次方程"在外圈（Prefill LB），仓库里没有。

## 设计取舍（本课最重要的部分）

| 取舍 | 选择 | 代价 | 收益 |
| --- | --- | --- | --- |
| 调度器语言 | C++ | 调试难、迭代慢 | decode 小 step 无 Python 开销 |
| 模型支持 | 单模型特化 | 无法复用 | kernel/结构可以深度定制 |
| 硬件 | 只做最新一代 | 用户面窄 | 能吃到 FP4/TMA 等新特性 |
| 服务层 | 不做 | 不能直接上线 | 引擎可以假设上游已做路由/缓存 |
| 抽象 | 少 | 扩展性差 | 代码路径短、性能可预测 |

这五条合起来，就是"生产框架"和"通用框架"的分水岭。

## 易错点

1. **以为 `LLM` 是 serving 入口**：它只是离线批量 API。
2. **以为 `vendor/` 是源码**：普通 clone 后是空目录，需要 submodule。
3. **以为 `num_gpu_blocks` 是配置**：它是启动时 profile 出来的。
4. **以为 `block_size` 可以随便改**：它和 kernel、state slot、128 边界都耦合。
5. **以为 `tests/` 能在 Mac 上跑**：`deepinfer._C` 编不出来。
