# 第 02 课：请求生命周期——从字符串到 token

> 本课把 `LLM.generate()` 拆成 7 个阶段，每个阶段给出输入、输出、状态变更和可观测点。

## 本课目标

1. 不看代码，能复述一个请求从字符串到输出的完整路径。
2. 能说出每个阶段的**数据结构**（`Sequence` / `SequenceMetadata` / `SchedulerOutputs` / `RequestOutput`）。
3. 知道在哪里下断点、打日志、加计时，能定位"慢在哪一段"。
4. 理解"指针 + 对象池 + 延后释放"这套输出机制为什么存在。

## 全景图

```
[1] tokenize          str → np.int32[]
[2] add_request       → Sequence（C++）→ scheduler.waiting
[3] schedule()        → SequenceMetadata[] + SchedulerOutputs
[4] execute_model     → forward → logits
[5] sample            → token ids + logprobs
[6] post_process      → 更新 Sequence 状态 / 判断结束
[7] 输出              → RequestOutput 指针数组 → Python 解码
```

## 阶段 1：tokenize

`LLM.generate()` 内部对每个 prompt 调 `tokenizer.encode`，得到 `list[int]`，再转 `np.int32`。

关键点：
- **引擎不收字符串**。`add_request` 的签名是 `prompt_token_ids: np.ndarray[np.int32]`。
- 多模态请求会先经过 `MultimodalProcessor.overwrite_prompt()`，把图像占位符替换成 image token 序列。
- 如果启用 Engram，还会生成一份**压缩词表**的 token（`CompressedTokenizer.encode`），两份 token 长度必须一致。

## 阶段 2：add_request

`deepinfer/engine/llm_engine.py:472`：

```python
def add_request(self, /, user_id, request_id, sampling_params,
                prompt_token_ids, multi_modal_data=None,
                arrival_time=None, extra=None, enqueue=True,
                chunk_checkpoints=None) -> Sequence | None:
```

它做了 9 件事（按顺序）：

1. `SamplingParams` 归一化（dict → 对象），补 `eos_id`；
2. YoCo 截断模式下强制关闭 `prompt_logprobs`（截断后无法算被裁掉的行）；
3. 多模态 prompt 改写；
4. 空 prompt 检查；
5. token 范围校验（`[0, vocab_size + ImageTokenOffset)`），非法直接丢弃请求；
6. 分配 `seq_id`，构造 `Sequence`（C++ 对象）；
7. 若 `so_args` 非空，提交异步 grammar 编译；
8. `scheduler.add_sequence(seq)` 入 waiting；
9. 返回 `Sequence` 供调用方引用。

注意 `enqueue=False` 的用法：调用方自己管调度（benchmark 会用它做"只建序列不入队"的预热）。此时 SO 编译必须同步完成，因为没有人会替你 `pump()`。

## 阶段 3：schedule

`LLMEngine.step()` 的第一段（`llm_engine.py:881`）：

```python
with cpu_timer.record("schedule"):
    seq_metadata_list, scheduler_outputs = self.scheduler.schedule(
        self.sequence_metadata_pool
    )
```

C++ 侧 `Scheduler::schedule()` 做四件事：

1. 调 `_schedule()` 选 batch（prefill 或 decode，见第 03 课）；
2. 校验 `num_batched_tokens <= max_num_batched_tokens`；
3. 为每个被调度的 seq 构造 `SequenceMetadata`（从对象池分配），计算 `seqlen_q/seqlen_k`、`position_end`；
4. 估算 FLOPs（只在 `log_stats` 时），累加 `sum_seqlen_qxk`、`max_seqlen_k`。

`SequenceMetadata` 是**每步的只读快照**：它把 `Sequence` 的可变状态"冻结"成这一 step 的输入，避免 worker 执行时序列状态又被调度器改掉。

## 阶段 4：execute_model

`worker.execute_model_step()` 的第一段：

- driver worker 先算 `total_q`，调 `_correct_seqlens_qk()` 处理 ZOS 下的长度修正；
- 调 `model_runner.execute_main_model(seq_metadata_list, gpu_cache, metadata_zos, total_q)`；
- 内部准备 `InputMetadata`（input_ids、positions、block_tables、seqlens、slot_mapping……），再调模型 forward。

模型 forward 的入口是 `DeepseekModel.forward()`（`models/deepseek.py:154`）：

```python
def forward(self, kv_caches, input_metadata, hidden_states=None, dflash=None):
    if hidden_states is None:
        hidden_states = self.embed_tokens(input_metadata.input_ids)
    ...
    for i in range(self.num_layers):
        if input_metadata.is_prompt and i == self.yoco_boundary_layer_idx:
            ...  # 切换 metadata 视图
```

这一段是第 06/07 课的主题，这里只需知道：**它返回 hidden states，不返回 logits**。

## 阶段 5：sample

`model_runner.execute_sample()` → `Sampler.forward()`（`layers/sampler.py:114`）→ `fused_sample` kernel。

输出打包成 `SamplerOutput`，包含：
- `token_ids`、`token_logprobs`、`top_logprobs`、`top_token_ids`；
- 投机的 `accepted_token_ids`、`accepted_token_logprobs`、`next_n_token_ids`、`next_n_token_confidence_rates`；
- SO 的 `so_status`；
- 统计量：`num_generated_tokens`、`num_verified_tokens`、`moe_load_balance_ratio`。

## 阶段 6：post_process

`LLMEngine.post_process()`（`llm_engine.py:984`）：

```python
def post_process(self, step_state: WorkerStepState):
    ...
    request_outputs, log_stats_func = self._process_model_outputs(output, scheduler_outputs)
```

`_process_model_outputs()` 做五件事：

1. `process_MTPInfo`：把本步的 draft token / confidence 写回 `Sequence`；
2. `scheduler.process_outputs(accepted_ids, output_ids, so_status)`：推进序列状态、判断 EOS/max_tokens/stop strings；
3. 统计完成的请求数、输出长度、payload 长度；
4. `build_request_outputs(...)`：构造 `RequestOutput`，放进 `RequestOutputPool`；
5. 打日志（`StepStats`）。

**关键设计**：`RequestOutput` 不在 Python 堆上逐个 new，而是由 C++ 池分配，Python 拿到的是 `np.uint64` 指针数组。调用方读完这一批后，下一次 `step()` 会自动释放；要保留必须 `pool.clone()`。

## 阶段 7：输出与解码

`LLM.generate()` 的循环：

```python
while engine.has_unfinished_requests():
    outputs = engine.step()
    for req_output in outputs:
        ...
```

`RequestOutput` 里每个 token 带 `token_id`、`token_logprobs`、`draft_tok`、`accept_tok`，所以 `examples/offline_inference.py` 能直接算接受率和 PPL。

## 图解：一个 step 的时间线

```
CPU  ──schedule──┬──launch forward──┬──post_process(N-1)──┬──launch sample──
                 │                  │                     │
GPU  ────────────┴──forward(N)──────┴─────sample(N)───────┴──forward(N+1)──►
                        ▲                                      ▲
                        └──────── ZOS 让这两段重叠 ────────────┘
```

非 ZOS 时，`post_process(N)` 会在 `sample(N)` 后同步等待，GPU 在 CPU 干活期间空转。第 04 课会量化这段空洞。

## 可观测点：在哪打断点/加日志

| 想知道 | 加在哪 | 看什么 |
| --- | --- | --- |
| 请求有没有入队 | `scheduler.add_sequence` 后 | `waiting.size()` |
| 这步是 prefill 还是 decode | `SchedulerOutputs.prompt_run` | 布尔值 |
| 每步 batch 多大 | `scheduler_outputs.num_batched_tokens` | 与 `max_num_batched_tokens` 比 |
| KV 命中多少 | `scheduler_outputs.num_cached_tokens_gpu` | 命中率 |
| CPU 时间花在哪 | `cpu_timer` | `schedule` / `run_workers` / `bubble` |
| GPU 时间花在哪 | `cuda_timer` + `PROFILE=1` | `device_forward` / `device_sample` |
| 投机接受率 | `SamplerOutput` 的 accepted/draft | 每步统计 |
| MoE 是否倾斜 | `moe_load_balance_ratio` | 接近 1 越好 |

`deepinfer/timer.py` 的 `cpu_timer.record("name")` 是上下文管理器，`StatsLogger` 会按 `DEEPINFER_LOGGING_INTERVAL_STEP` 聚合打印。

## 易错点

1. **`SequenceMetadata` 不是 `Sequence`**：前者是每步快照，后者是全生命周期状态。
2. **`add_request` 可能返回 None**：token 非法/VE 失败时请求被丢弃，不会抛异常。
3. **输出指针会失效**：跨 step 持有 `RequestOutput` 必须 `clone`。
4. **prefill 和 decode 走同一个 `execute_model_step`**：靠 `is_prompt` 分支，不是两套函数。
5. **ZOS 下 `post_process` 处理的是上一步**：调试时看到"输出晚一步"是正常的。
