# 第 05 课：KV 缓存——block 与 state 为什么是两套

> 大多数框架只有一个 paged KV pool。DeepInfer 有两套：**paged block** 和 **state slot**。
> 本课解释它们的边界、布局、生命周期，以及"前缀命中"到底发生在哪一层。

## 本课目标

1. 说清 `KVCache`（paged block）和 `StateBlock`（state slot）的职责边界。
2. 理解 `KvCacheState` 的每个字段，尤其是 `num_tokens` / `hit_tokens` / `swa_valid_start`。
3. 能解释 FP4 主 KV、MXFP4 indexer KV、MXFP8 SWA 的 scale 粒度差异。
4. 知道 fork/COW 怎么工作，以及为什么引擎内没有 radix tree。

## 两种缓存，一张表

| 维度 | Paged block KV | State slot |
| --- | --- | --- |
| 管理类 | `BlockManager`（C++） | `BlockManager`（同一个类，另一个实例） |
| ID | `block_id` | `state_id` |
| 粒度 | `block_size` token | 每序列一个固定 slot |
| 存什么 | 主 KV（压缩后）+ indexer KV | SWA KV + 压缩状态（`ca_state`/`ica_state`） |
| 何时写 | 每个 prefill/decode step | 只在 128 token 边界 |
| 是否进前缀缓存 | 是（外部 KV store） | 否（只在产生它的机器内存里） |
| 是否可重算 | 是 | 是（bounded replay） |
| 容量参数 | `num_gpu_blocks` | `num_state_seqs` |

为什么分开：
- 生命周期不同：block 随序列增长，state 是"环形窗口"；
- 访问模式不同：block 按 token 随机读写，state 是整块拷贝；
- 存储介质不同：block 可以落 3FS，state 只在 host memory；
- 命中策略不同：block 命中看 hash 链，state 命中看"最近 128 token 有没有存"。

## 源码：KvCacheState

`csrc/engine/sequence.hpp`（约 199 行）：

```cpp
struct KvCacheState {
    int block_size{0};
    int previous_num_tokens{0};
    int num_tokens{0};
    int hit_tokens{0};
    int swa_valid_start{0};
    std::vector<int> block_table;
    int state_id{-1};
    int last_copy_state_token_idx{0};

    void set_num_tokens(int value);          // 外部注入命中数时同步基线
    void advance_optimistically(int n);      // ZOS：先加，后提交
    void commit_processed_tokens(int n);
    void reset_for_recompute();              // 抢占重算：全清
};
```

字段含义：

| 字段 | 含义 | 谁写 |
| --- | --- | --- |
| `num_tokens` | 当前已有 KV 的 token 数 | 调度器/worker |
| `previous_num_tokens` | ZOS 乐观推进前的基线 | `advance_optimistically` |
| `hit_tokens` | 外部前缀命中的长度 | entrypoint/KV store 注入 |
| `swa_valid_start` | SWA 窗口的有效起点 | YoCo/state 逻辑 |
| `block_table` | 逻辑块 → 物理块 | 调度器分配 |
| `state_id` | 对应的 state slot | `_clone_state` / 分配 |
| `last_copy_state_token_idx` | 上次拷贝 state 的位置 | `do_copy_state` |

**关键**：`num_tokens` 和 `hit_tokens` 是两件事。前者是"显存里真有这么多 KV"，后者是"上游告诉我们前缀命中了这么多"。如果 `hit_tokens > 0` 但 block 没加载，引擎会读到脏数据——所以 `add_request` 之前必须把 KV 拉进显存（这是 entrypoint/KV store 的责任，不在本仓库）。

## BlockManager：极简到只有链表

`csrc/engine/block_manager.hpp:19`：

```cpp
struct Blocks {
    Blocks(int _n) : _blocks(_n), _head(1), _tail(_n - 1), _size(_n - 1) {
        TORCH_CHECK(_n > 1, "GPU blocks 太少了: ", _n);
        for (int i = 1; i < _n; ++i) { _blocks[i].prev = i - 1; _blocks[i].next = i + 1; }
        _blocks[_n - 1].next = 0;
    }
    int allocate();      // pop_front + ref_count++
    void free(int id);   // ref_count--，归零才 push_back
    void pin_block(int id);  // ref_count++（共享）
};
```

三个细节：
1. **0 号块不用**，所以 `_head` 从 1 开始，`0` 表示"空指针"；
2. **refcount 支持共享**：fork 请求会 pin 父请求的 block；
3. **没有 hash / LRU / radix tree**：分配就是拿空闲链表头，释放就是 refcount 归零后放回尾部。

这意味着：**引擎内没有自动前缀缓存**。同一个前缀的两个请求，除非显式 fork，否则会各占一份 block。

## 前缀命中在哪一层

Q&A 的设计：

```
Entrypoint（3 台）
  └─ 哈希链前缀匹配（只查 metadata）
      └─ 命中长度 L1
          └─ 把 L1 注入 Sequence.cache.hit_tokens
              └─ 调度器只分配 L1 之后的 block
                  └─ KV 数据由独立进程从 3FS 异步拉到 host，再 swap-in 到 HBM
```

代码证据：
- `KvCacheState.hit_tokens` 由外部注入；
- `_schedule_prefill` 里 `seq->cache.num_tokens` 已经包含命中部分；
- `prefix_caching_hit` 只在 `block_table.empty()` 或 `branch_id` 以 `_` 开头时为真（fork）。

所以：
- **跨请求前缀复用**：引擎外（3FS + Entrypoint）；
- **同请求 fork 复用**：引擎内（pin + COW）；
- **引擎内自动缓存**：没有。

这是与 vLLM（block hash 自动前缀缓存）/ SGLang（RadixAttention）最本质的差异之一。

## FP4 的两种 scale 粒度

`model_metadata_utils.py`：

```python
def derive_main_kv_cache_num_per_channels(cfg, is_swa):
    """FP4 主压缩 KV 每 16 个值共用 scale；MXFP8 主 KV 和 SWA 每 32 个值共用 scale。"""
    return 16 if not is_swa and cfg.use_fp4_sparse_kv else 32
```

Q&A 的完整口径：

| 内容 | 格式 | scale 粒度 |
| --- | --- | --- |
| 主 KV | FP4 e4m3 | per-16（类似 NVFP4，无 global scale） |
| Indexer KV | MXFP4 ue8m0 | per-32 |
| MoE routed expert 权重 | MXFP4 ue8m0 | per-32 |
| SWA KV | MXFP8 | per-32（528 B/token） |

为什么主 KV 用 per-16：主 KV 是精度最敏感的（直接影响 attention 输出），更细的 scale 能减少量化误差；indexer 只用来打分选块，粗一点没关系。

## State slot 的内部结构

Q&A 描述（代码里对应 `StateBlock` / `select_state_slice_to_store`）：

```
每个序列一个 slot：
  [ stored region: SWA ][ dropped region: YOCO consumer SWA + ca_state/ica_state ]
```

- stored region：需要跨请求保留的 SWA 窗口（前 20 层）；
- dropped region：YOCO consumer 层的 SWA（靠 prefill 重算恢复）+ 压缩边界累加器；
- 只存 128 token 的倍数；
- decode 时在 device 上留一个 replica region，每跨 128 边界拷一次，结束时从 replica 取。

数据量（Q&A）：

```
20 层 × 134 token × 528 B = 1,415,040 B ≈ 1.35 MiB / 序列
```

`134 = 128 窗口 + 6 个回溯 token 的余量`。

## fork 与 copy-on-write

两个场景：

1. **prefill 侧的 branch**（`branch_id` 以 `_` 开头）：多个请求共享同一段 prompt 的 KV，各自只算后缀；
2. **prompted → running 的 forked seq**：`_schedule_decode` 的 `admit` 里克隆 state 和尾 block。

COW 的实现（`scheduler.hpp:397`）：

```cpp
auto new_blocks = block_manager->allocate_nolock(to_allocate_blocks);
if (seq->cache.num_tokens % seq->cache.block_size) {  // 尾块写了一半
    clone_blocks.emplace_back(seq->cache.block_table[num_reserve_blocks]);
    clone_blocks.emplace_back(new_blocks.front());
}
for (size_t i = num_reserve_blocks + ...; i < seq->cache.block_table.size(); ++i) {
    clone_blocks.emplace_back(seq->cache.block_table[i]);
    clone_blocks.emplace_back(0);   // 0 = 新块，之后由 worker 填
}
```

为什么要 COW：fork 时父请求可能还在 decode，共享块会被继续写；只有尾块可能被两个请求同时写，所以先复制尾块。

## 容量与水位

- `num_gpu_blocks`：启动时 profile 显存后算出来（`_init_cache`）；
- `GPU_CACHE_PREFILL_WATERMARK = 0.9`：超过 90% 就不再做 prefill，防止 decode 没块可用；
- `num_state_seqs`：按 `max_num_seqs` 算，`DEEPINFER_NUM_STATE_SLOTS_RATIO` 可调；
- `block_size`：与 kernel、128 边界、CP 对齐都耦合，不要随便改。

## 图解：一个序列的缓存生命周期

```
add_request
  │  hit_tokens = L1（外部注入）
  ▼
prefill
  ├─ 分配 ceil((L1 + suffix)/block_size) 个 block（前 L1/block_size 个来自命中）
  ├─ 写主 KV + indexer KV
  └─ 最后一块 prefill 结束时，把 SWA 写到 state slot（128 对齐）
  ▼
decode
  ├─ 每步 _append_slot() 分配新 block（尾块 COW）
  ├─ 每跨 128 token，把 SWA 窗口拷到 replica region
  └─ 请求结束：从 replica 取最后一次完整拷贝 → state store
  ▼
释放
  free_seq：state_manager.free(state_id) + block_manager.free(block_table)
```

## 易错点

1. **把 `hit_tokens` 当成 block 已加载**：它只是"应该命中"，数据要另外拉。
2. **以为 decode 会把 KV 卸载到 CPU**：Q&A 明确说 decode 不 offload（不受容量限制）。
3. **以为 SWA KV 也在 paged block 里**：它在 state slot，介质是 host memory。
4. **改 `block_size` 只改配置**：kernel、CP 对齐、128 边界都会错。
5. **以为 fork 是零拷贝**：尾块要复制，state 也要克隆。
