Scheduler · Why C++

把调度器搬进 C++：一次明确的取舍

Python 调度器的成本

  • 每个 seq 的字段访问都走对象协议
  • 高频小对象触发 GC 抖动
  • decode 步只有几毫秒，CPU 占比被放大

C++ 调度器的代价

  • 调试跨语言，Python 断点看不到内部
  • 改调度要重编译
  • pybind 接口手写，字段变更要同步 .pyi

判断：只有“模型固定、流量巨大、值得为每微秒优化”的团队才该学这招。通用框架选 Python 是对的。

Scheduler · State

三个队列，一条状态机

waiting
新请求 / 被抢占重算 ──prefill──▶ prompted
prefill 完成，待转入 ──admit──▶ running
decode 中
  • decode 步必须清空 running：每个 seq 要么被调度、要么被抢占，TORCH_CHECK(l == r)。
  • 被抢占的请求：reset_for_recompute() 后 push_front(waiting)，下一轮重新 prefill。
  • 锁：BlockManagerMutexAcquire 同时锁 block 和 state 两个管理器。
Scheduler · Voting

全员都想做才做

每 prefill_attempt_interval 步。防“一个 rank 干活、其他 rank 陪跑空 prompt”。

ANY 点

任一 rank 想做就做

每 prefill_any_attempt_interval 步。给孤立 rank 兜底，防饿死。

Scheduler · Decode

LCFS + 抢占：尾延迟优先

按 output_len 降序排→ 从最短的开始调度→ 块不够？从最长的抢

抢占后：重算

reset_for_recompute()，回到 waiting 队头。适用于普通请求。

抢占后：结束

stop_preempted_request=true 或请求带 SO 状态（自动机不能重算）。

为什么 LCFS：让短请求尽快完成，降低平均排队；长输出本来就要跑很久，抢它重算的边际成本更可控（推断）。

Scheduler · Invariants

调试先看这 6 条断言

1. sum(seqlens_q) == num_batched_tokens <= max_num_batched_tokens 2. seqlen_q + cache.num_tokens <= seq.get_len() 3. position_end <= runtime_max_model_len 4. decode 步 running 必须清空（全部调度或抢占） 5. COMPLETION 必须 stop_preempted_request=true 6. nextn>0 时，MTP info slot 使用数 == running 大小

这些不是“注释里的建议”，是 TORCH_CHECK。线上撞到任何一条，先回看是哪一步的调度状态被破坏了。

ZOS · Problem

decode 一步里，GPU 有两段空转

GPUforward(N)idlesample(N)idleforward(N+1)
CPUschedule(N)launchwaitpost(N)schedule(N+1)
  • post_process(N) 必须先拿到 sample 的 GPU→CPU 同步结果。
  • decode 的 step 是毫秒级，CPU 这两段可能占 5%–20%；batch 越小占比越高。
  • ZOS 的目标不是“调度更快”，而是“调度时 GPU 不空转”。
ZOS · Pipeline

把 CPU 提前一步

GPU: forward(N) ─────────────► sample(N) ──────────► forward(N+1) CPU: schedule(N+1) → launch_forward(N+1) → post_process(N-1) → launch_sample(N+1)
1

forward(N)

当前步主模型

2

post(N-1)

补上一步的后处理

3

sample(N)

当前步采样

4

延迟 post(N)

留给下一步 forward 重叠

顺序不能换成 1→3→2：那样 post(N-1) 要等 sample 同步，白等。

ZOS · Costs

三个新问题，三套补丁

资源晚释放

DeferredRelease：本步产出挂起，下一步 pre_sampler_sync 才释放。

空 rank 也要动

placeholder step：跑一个假 forward，保持 DP 组步型一致、NCCL 不超时。

长度未知

CPU 乐观估计 seqlens_q；GPU 用 D2H 回来的真实值修正 metadata。

代价：输出“晚一步”、调试难、资源生命周期变长；收益：稳态下 GPU 的 forward→sample→forward 没有 gap。

YoCo / CED

prefill 只跑前一半层

encoder · 20 层（prefill 全算）
decoder / consumer · 20 层（只算后缀）
  • CED：decoder 的 global KV 由 encoder 最后一层 hidden 投影而来，不逐层自算。
  • 代码：cfg.n_prefill_layer 之后是 consumer；forward 在边界层切 metadata 视图。
  • 激活参数：外部资料称 prefill 8B / decode 16B；代码只认配置，不写死。

20/20 为外部资料，代码只认 n_prefill_layer。这是“模型结构直接长进推理引擎”的典型：省的不是调度，是整段计算。

YoCo · Two Modes

mask 与 compact：一个改可见域，一个真删行

MASK

不真截断

  • 仍算完整 token 行
  • 把矩形外的 SWA 可见域置空（整行 -1）
  • 实现简单，几乎不省算力
COMPACT

真的只留后缀

  • gather 出保留行，组成更短 varlen
  • hidden / residual / topk / candidates 一起搬
  • 约省一半 prefill 计算

两者共用同一个 SWA 可见域公式，所以在保留区间内数值一致 —— 这是 examples/yoco/ 要验证的。

YoCo · Bounded Replay

重算 128 个 token，而不是 2,560 个

prefix cache 命中
replay 128
+6
1命中上限 = L − 134（128 窗口 + 6 回溯）
2先查 block KV → L1（128 的倍数）
3再查 [L1−128, L1] 的 SWA：有则命中 L1
4没有则退一个 block 到 L1−128，重放补齐

近似结果只用于 decode，不进入 prefix cache，避免误差累积。

Attention · CSA2

一个 attention 类，四种机制

压缩 KV（C1/C2）

gated low-rank 压缩；只允许 ratio ∈ {0,1,2}，C4/C128 已删除。

稀疏索引（MQA）

relu(q@k)·w 打分 → top-k 选块；单头，不用 softmax。

SWA

局部窗口兜底；与稀疏选中的全局块拼接。

跨层共享

Full / Reindex / Reuse：共享 main KV、indexer K 或 top-k 索引。

约束：稀疏必须配 SWA；不开 SWA 必须有 packed KV；indexer 头数必须全局唯一。

EPLB · Algorithm

两步：先决定复制谁，再决定放哪张卡

STEP 1

冗余给谁

每轮给一个专家加副本，选“加完后最大每副本负载最低”的那个。

score = tokens / logical_count score_added = tokens / (count+1) argmin( max(score with one replaced) )
STEP 2

放哪张卡

逐层贪心：最小化各 step 的 rank 峰值之和。

minimize Σ_step max_rank(load)

搬权重走 NVLink symm_mem 原地交换；decode 1 万步重排一次，prefill 1000 步。

DSpark · Idea

固定验证 5 个，是浪费还是保险？

固定长度

每条请求都验证 5 个 draft。实现简单、可预测；但低概率 token 也在花验证算力。

verify = 5.0

DSpark 变长

confidence head 预测每个 draft 的接受率，按期望收益排序，选前缀子集。

verify = 3.2 – 4.4

平均接受长度几乎不变（3.29 → 3.20），验证算力少 ~30%。

DSpark · Scheduling

两个队列，两个时间尺度

N-2 轮

决定总预算 best_bsz

总量错误代价大，用更旧、更稳的接受率。

N-1 轮

分配每请求长度

相对新，用于给高接受率的 draft 加格子。

throughput(bsz) = expected_tokens / (baseline_ms + slope_ms × graph_size + sampler_ms) expected_tokens = num_seqs + Σ accept_rate(draft)

按“单个 draft token”分配，不是按请求；一个请求可能拿到 0–5 个。ZOS 下这一步搬到 GPU（cumprod + global rank + remap）。

Sampler

三件事：融合、可复现、可约束

Fused

温度、top-k/p、log-softmax、采样、SO mask 一个 kernel 完成，避免 logits 反复读写。

Batch-invariant

固定 reduction 顺序；不同 batch 组成下 bit 级一致（NVIDIA）。

Deterministic

hash 随机数 + 固定 seq_seed + 关 MTP varlen；相同输入相同输出。

# fused_sample.py — 一个 kernel 里做完五步 temperature → top-k/top-p → log-softmax → sample → (optional) logprobs / SO mask

没有确定性，tests/models/offline_decode_ppl.json 的逐样本 PPL 金标准就无法比对。

Structured Output

schema / regex / EBNF→ XGrammarCompiler

Comparison · Five Shifts

五个“选择”，不是五个“优化”

C++调度器换语言：用可维护性换 decode 小 step 的确定性开销。
3FS前缀缓存外移：用系统复杂度换任意前缀命中与存储/计算解耦。
EP放弃 TP：MoE 只传 token 不传权重，配合 EPLB 摊薄每卡访存。
DSpark投机从固定长度变成按边际收益分配验证算力。
单模型一个模型榨干两代硬件，而不是一个引擎适配 N 个模型。

Self-test

能答上这 5 题，就算读懂了

Q1为什么 NORMAL 引擎需要两轮 allreduce？第二轮防的是什么死循环？
Q2ZOS 下为什么 post_process(N-1) 必须放在 forward(N) 之后、sample(N) 之前？
Q3YoCo 命中策略里，134 从哪来？为什么重放结果不能进 prefix cache？
Q4EPLB 为什么按“多 step 峰值之和”排布，而不是平均负载？
Q5DSpark 为什么用 N-2 轮接受率选总预算、N-1 轮分配每请求长度？

答案分别在 docs/03、04、06、08、09。

Pitfalls

八个最容易踩的坑

1. vendor/ 是 submodule，普通 clone 是空目录。

2. H100/A100 跑不了：只认 SM10。

3. 没有在线 server，LLM 只是离线批量。

4. hit_tokens ≠ 数据已加载。

5. 自己写循环忘了 pump()，SO 请求永远不入调度。

6. ZOS 下加 .item() 会触发同步守卫。

7. 改 block_size 不只是改配置，kernel/CP/128 边界都耦合。

8. 低并发开 MTP varlen 可能负收益。

One Page

一页纸总结

定位DeepSeek 生产框架的开源子集：离线、单模型、两代硬件。
结构C++ 调度器 + Python 编排 + TileLang kernel + EP/DP，无 TP。
三招牌ZOS 流水线、YoCo bounded replay、DSpark 变长验证。
最大差异前缀缓存在引擎外（3FS），引擎内只有 fork/COW。
性能prefill 60–88k；decode 2.5–26k tok/s/GPU（交互性 325–104）。
学习价值看“通用框架如何为单一模型做外科手术”。
Fin

读它，不是为了用它。
是为了知道“快”可以被拆成多少个小决定。
